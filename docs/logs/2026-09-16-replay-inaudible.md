# 2026-09-16 · 回放听不见：不是音量，是根本没播

用户在现场报告两件事,先后发生:

1. 「播回我说话的声音很低」
2. 「你回播的时候,我并没有听到你的声音」

这两句听起来像同一个问题的轻重两级,**实际是两个不同的故障**,差点被我合并处理。

## 第一个：确实偏小，但不是 bug

| | 峰值 | RMS |
|---|---|---|
| 回放(录音原样) | **-23.3 dBFS** | -40.5 dBFS |
| turn06 原始素材 | **-8.4 dBFS** | -25.8 dBFS |

低约 **15 dB**。原因是录的是 AFE 输出——电平由麦克风拾音决定,人在一两米外、
PGA 30dB,峰值只占满量程 7%。**原样播出去当然小。**

修法:上传前**峰值归一化到 -6 dBFS**,增益上限 +24dB(防止一段没人说话的窗口把
底噪放大到满刻度),且只增不减。实测那次 `peak=3046 gain=5.4x`。

## 第二个：完全没出声，而且我差点归因错

第二句我一开始也当成"更小声"来处理。真去量才发现是另一回事:

```
回放命令 status=failed  msg=stage=wav_start error=ESP_ERR_INVALID_STATE
```

`wav_start` + `INVALID_STATE` = `busy_` 抢占失败,**播放器当时是忙的,这次回放
一个采样都没播出去**。用户听到的不是"很小",是**静音**。

树莓派房间录音印证:17–21s 有 -2~-7 dBFS 的大声(机器人说 turn06),此后再无第二段。

### 为什么之前两次是好的

因为这是**竞态**。回放走的路径是:设备上传 → hub 入队 `play_audio` →
**下一次心跳(5s)下发** → 播放。它必须赢过"刚被打断的那一轮播放释放 `busy_`"。
前两次赢了,这次输了。

**竞态最坏的地方不是失败率,是它让前两次的成功变成了误导性证据**——我当时拿
"status=done" 当成"这条路可靠",还去改音量。

## 修法：不去赢竞态，而是消掉它

录音本来就在设备的 PSRAM 里。**上传到云端、等云端下发命令、再下载回来播,
这一整圈是多余的。** 改成直接 `board_spk_write()` 从缓冲播出去:

- 没有竞态可输
- 去掉了"你说完"到"你听到自己"之间的上传和往返,而这个间隔正是这个演示要展示的
- 仍然照常上传(`play=0`)存档,便于事后复听

附带一个合意的副作用:直接写编解码器绕过 `AudioPlayer`,所以**回放期间打断检测
不武装**——机器人不该把自己的回放当成需要被打断的东西。

## 顺带修掉的两个工具问题

1. **ssh 起的后台 `arecord` 被杀**。`nohup ... &` 不够,通道关闭时仍被 SIGHUP,
   症状是录音文件根本不出现。改用 `setsid ... </dev/null & disown`。
2. **没清场就起演示**。播放器还忙着时启动 `echo_demo`,失败在 `stage=speak_start`,
   而那次"机器人开口"(+1.0s)其实是上一轮的遗留播放——**看起来一模一样**。
   现在先 `stop_audio` 并等 `audio_playing` 落回 False 再开始。

## 教训

用户报"听不见",我的第一反应是调音量——因为**上一个问题恰好就是音量**。
如果不是去量了回放命令的状态,我会把一个"根本没播"的故障,用调音量的方式
"修"到看起来更好一点,然后继续错下去。

**相邻的两个症状不一定是同一个原因。**
