# 2026-09-16 · E5 是勉强通过，不是通过；门限的依据算错了统计量

## 浸泡数据

| 浸泡 | 起始 uptime | 切断 |
|---|---|---|
| A（v92） | ~1.5–2 小时 | **5 / 20** |
| B | 200s | 0 / 20 |
| C | 838s | 1 / 20 |
| D | 1438s | 1 / 20 |
| E | 2034s | 0 / 15 |
| F | 2482s | 0 / 15 |

重启后合计 **2 次 / 90 段**,约每 1200s 播放出现一次误打断。
**E5 的判据是「0 次 / 127s」** —— 单次 127s 运行大约有 10% 概率撞上一次。
**所以历史上那些"通过"多数是运气,E5 实际是勉强通过。**

`uptime 越久越容易切` 的假设**不成立**:200s→2482s 之间是 0,1,1,0,0,没有单调趋势。
唯一的高发是 v92 那次(5/20),处在另一个时段,成因未定,**不写成结论**。

## 真正扎实的发现

一次切断的门限归因:

```
frames=363  loud=46  speech=1  both=1  max_rms=151
```

**机器人独播时,363 帧里有 46 帧(13%)的 AFE 输出越过了打断门限 40。**
另一次更极端:`max_rms=1073`。

而当初 `AEC_BARGEIN_MIN_RMS=40` 的依据写在代码注释里:

```
robot alone (E1 @vol80)   post_rms   8.5
human voice (E2b)         post_rms 218.6
21-26x apart ... A threshold at 40 sits ~4.5x clear of both.
```

**8.5 是一个窗口的平均 RMS,而门限判的是每一帧的 RMS。**
用平均值去论证一个对逐帧最大值生效的门限——**统计量用错了**。
逐帧最大值实测能到 151 和 1073,比那个"4.5 倍余量"高一到两个数量级。

**真正在挡住误打断的不是电平门限,是 VAD**(363 帧里只判了 1 帧语音)。
电平门限被routine突破;两者恰好在同一帧同时成立时,误打断就发生。

## 为什么简单地抬高门限不行

人声在双讲时的 `max_rms` 实测 294–831,而机器人残余能到 1073。
**两者的逐帧峰值是重叠的**,单一电平门限分不开。抬高门限会同时削掉真打断。

要做对,得先拿到**两类信号逐帧 RMS 的分布**(不是各取一个数),
在分布上找工作点——而这正是任务清单 T0.4 要求的"离线分析"。
采集基础设施已经有了(`aec_capture` 三路 + 归档),缺的是这一步分析。

**我这次不动参数。** 今天已经有五条结论是因为拿单点数字当依据而被推翻的,
再凭两个 `max_rms` 去调门限就是第六条。
