# 2026-09-14 · E5 三轮：把打断接进生产播放路径暴露出的共享状态假设

## 一句话

E5 名义上测的是"误打断率"，但它三轮跑下来一次都没有测到误打断（本地误触发始终
是 **0 次 / 127 秒**）。真正的产出是它连续抓出了 P3 改动引入的**两层回归**，而抓到
它们靠的不是误触发计数，是脚本里那个独立校验：**每段音频有没有播满自己的时长**。

## 背景：为什么 v40 之前跑 E5 没有意义

打断检测器门控在 `playback_is_playing()`，而它只反映 `playback.c` 的 TTS 分句队列。
机器人真正说话走的 `AudioPlayer`（`play_audio` / `play_lan_audio` / `speak_pcm`）
直接往 codec 写数据，从不注册。所以 v40 之前：

> 检测器在机器人说话期间根本不评估 → 跑 E5 必然得到"0 次误打断"→ **假通过**。

v40 把生产播放路径接进去（注册 external-active + 外部停止回调），E5 才有意义。

## 第一轮（v40）：`playback_kill()` 语义被混用

```
turn02  音频 7.92s  实播  3.16s  failed  ← 被切断
turn04  音频27.20s  实播 27.60s  done
turn06  音频27.28s  实播 27.64s  done
turn08  音频27.20s  实播 27.55s  done
turn10  音频37.92s  实播 20.68s  failed  ← 被切断
本地误打断：0 次
```

串口日志里两次切断前的序列一模一样：

```
E transport_ws: Error transport_poll_write(0)
W ws: ws error → disconnected → Reconnect after 2000 ms
I audio_player: WAV playback stopped
```

`ws_client.c` 在 `WEBSOCKET_EVENT_DISCONNECTED` 调 `playback_kill()` 丢弃残留 TTS
分句——这本身是对的。但 v40 让 `playback_kill()` 连带停外部播放器，于是**一次网络
抖动切断了跟云端毫无关系的本地播放**。

**修法（v41）**：拆开两种语义。

| 函数 | 含义 | 调用方 |
|---|---|---|
| `playback_kill()` | 发生了打断，停一切 | 本地打断检测器 |
| `playback_discard_stream()` | 云端 TTS 流没了，只丢它的分句 | WS 断连、云端 `tts_cancel` / `speech_start` |

顺带把云端信号也划到后者：云端根本不知道本地在播 `play_audio`，而 `speech_start`
是每次 VAD 起点都发的（包括残余回声误触发的）。让它硬停本地播放只增加故障模式。
这也正是 T3.1 说的"判定在本地做，不等云端"——而且只有本地路径快到能满足 <200ms。

## 第二轮（v41）：症状变了，而且更隐蔽

```
turn02  音频 7.92s  实播  8.24s  done
turn04  音频27.20s  实播 27.58s  done
turn06  音频27.28s  实播 15.07s  done   ← 仍被切断
turn08  音频27.20s  实播 27.52s  done
turn10  音频37.92s  实播  7.66s  done   ← 仍被切断
本地误打断：0 次
```

注意状态从 `failed` 变成了 **`done`**。串口给出了关键证据：

```
WAV raw stream bytes=1213440 read_result=622 final_PA_GPIO17=0 elapsed_ms=7421
WAV playback finished
```

**37.92 秒的音频，1213440 字节全部写完，只用了 7421 毫秒，而功放是关着的。**

不是截断——是**整个文件被以约 5 倍速冲进了一个已经关闭的输出通道**。

根因：v41 只拦住了 `stop()` 调用，但共享的清理逻辑 `playback_discard_queue()` 里
还有一行 `board_pa_enable(false)`。功放一关，codec 不再提供背压，`AudioPlayer` 的
写循环就不再被采样率节流，飞速跑完全部数据然后**报告成功**。

这比第一轮更危险：v40 至少还报 `failed`，v41 报 `done`——**静音、截断，而且只看
状态完全看不出问题**。

**修法（v42）**：功放和"已停止"状态上报是**跨播放器共享的资源**，`playback.c` 只有
在没有外部播放器活跃时才能动它们：

```c
if (!s_external_active) {
    report_state(false);
    board_pa_enable(false);
}
```

`AudioPlayer` 自己每条播放路径都成对管理 `AudioCodec_EnableOutput`，不会有遗留。

## 教训

把"打断"接进一条**从来没参与过打断**的播放路径，会把所有隐含的共享状态假设一次性
暴露出来。这次暴露了两层，而且是同一个模式的两个层次：

1. **函数语义共享**：`playback_kill()` 同时被"真打断"和"连接清理"调用，两者对外部
   播放器的期望完全相反。
2. **硬件资源共享**：功放 GPIO 和播放状态上报被 `playback.c` 单方面持有，但实际上
   是两个播放器共用的。

两层都不是靠 E5 本来要测的指标发现的——**误触发计数三轮都是 0，看起来一直很正常**。
发现它们靠的是脚本里那个"每段是否播满时长"的独立校验，以及把它和串口时间线对上。
单一指标看起来健康不等于系统健康，这是这次最值得记住的一条。

## E5 本身的结论（截至 v41）

- **本地误打断：0 次 / 127 秒**，三轮一致，房间安静。这一半是通过的。
- 完整通过还需要 v42 之后重跑一次，确认没有任何片段被提前结束。
- 需要注意：现在测的是"**没人说话时会不会误触发**"。等树莓派恢复后还要测
  E3/E4——"**有人说话时能不能真的打断**"。两件事都成立，打断功能才算立住。
