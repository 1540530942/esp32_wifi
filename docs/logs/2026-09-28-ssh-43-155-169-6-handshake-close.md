# 腾讯云服务器 SSH 直连握手中断：Clash TUN 全局代理接管

## 背景

用户反馈以前可用的 `ssh ubuntu@43.155.169.6` 现在无法连接，并确认目标为腾讯云 Ubuntu 服务器，可通过网页远程登录。

## 排查证据

- 本机直连 `43.155.169.6:22` 时，TCP 层显示已建立连接，但在收到 SSH 服务端版本字符串前就被关闭，报 `kex_exchange_identification: Connection closed by remote host`。认证尚未开始。
- 用户通过腾讯云网页远程确认：`sshd -t` 无报错；`ssh.service` 运行中；22 端口在 IPv4 和 IPv6 地址上监听；日志中其他公网地址能进入密码认证阶段。
- 曾误把 `korea` 别名当成另一台机器作交叉验证。复查 `ssh -G korea` 后发现它也映射到 `43.155.169.6`；这次尝试不能作为独立来源证据，已在会话中纠正。
- 本机直连另一台已登记的腾讯云主机 `110.40.154.41:22` 也在握手前被关闭；本机连接 `lv_server` 的 `39.156.151.204:58889` 正常。
- 从 `lv_server` 到目标机的 22 端口能完成 SSH 握手。随后用 `ssh -J lv_server ubuntu@43.155.169.6` 配合本机原有密钥成功登录，目标机返回主机名 `VM-0-5-ubuntu`、用户名 `ubuntu`。
- 目标机 `iptables` 的 INPUT 链经过 `YJ-FIREWALL-INPUT`，其中有大量针对 22 端口的单个地址拒绝规则；未查到本机通过公网查询获得的 `1.215.180.36`。后续证据排除了目标机防火墙是本次故障根因的判断。
- 2026-09-29 复查：目标机用 `tcpdump` 抓新的 SSH SYN 包，在同一窗口中能看到 `lv_server` 发来的连接，却看不到本机关闭跳板后的直连请求。Windows 宿主到该 IP 的默认路由走 `Meta Tunnel`，源地址显示 `198.18.0.1`；Clash Verge 运行配置为 `mode: global` 且 TUN 已启用，侧车日志明确记载 `43.155.169.6:22 using GLOBAL`。
- 在 Windows 临时加入目标 IP 的 `/32` 物理网卡路由后，`ssh -o ProxyJump=none ubuntu@43.155.169.6 'hostname; id -un'` 立即成功。因此故障由本机切换 Clash Verge 虚拟网卡模式后，`GLOBAL` 代理接管该 SSH 流量导致；不是腾讯云 sshd、密钥或用户配置错误。代理出口为何关闭 22 端口连接没有继续追查，因为该服务器应直连。

综合判断：原先使用系统代理时 SSH 直接出站；切换到 TUN 虚拟网卡后 SSH 也被接管，且全局模式将 22 端口送往代理。客户端显示 TCP 已连接只是 TUN 接收了连接，不能证明目标机收到报文。

## 修复

上一轮临时给本机 `/home/archer/.ssh/config` 增加 `ProxyJump lv_server`，只恢复了登录，未解决根因。2026-09-29 已移除这两处跳板设置，配置恢复为无跳板。修改前配置备份仍在 `/tmp/ssh-config-before-43-155-169-6`。

在 Windows 路由表加入 `43.155.169.6/32` 经 `WLAN` 网卡、下一跳 `192.168.1.1` 的持久路由，只让该服务器绕开 Clash TUN。先用 `ActiveStore` 临时路由验证，再移除临时路由，用默认存储创建同一规则，并通过 `Get-NetRoute -PolicyStore PersistentStore` 确认已持久化。目标机 SSH 服务和防火墙未改动。

验证：`ssh -G ubuntu@43.155.169.6` 不再显示 `proxyjump`；原命令 `ssh ubuntu@43.155.169.6 'hostname; id -un'` 和 `ssh korea 'hostname; id -un'` 都直接返回 `VM-0-5-ubuntu` / `ubuntu`。

## 现状与后续

本机原有命令现已无需跳板直接使用。持久路由绑定当前 `WLAN` 网关 `192.168.1.1`；若换网络、网关或服务器公网 IP，需要更新该目标路由。Clash Verge 官方文档也提供 TUN 流量排除选项，可作为将来改用应用内配置的路径：https://clashvergerev.com/en/guide/bypass 。

仓库同步：初次 `git fetch origin` 在沙箱内因 `.git/FETCH_HEAD` 只读失败；授权后直连 GitHub 22 端口又被 Clash 全局代理关闭。使用 GitHub 官方 `ssh.github.com:443` 入口并验证现有密钥后，成功执行 `git fetch origin`。同步后本地分支与远端跟踪分支一致。
