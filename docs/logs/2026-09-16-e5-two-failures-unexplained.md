# 2026-09-16 · E5 连失两次，随后连过四次，成因未定

## 事实

| 运行 | 结果 |
|---|---|
| e5_full_run（v92） | **切 1 次**（turn08 @ 7486/27200） |
| e5_full_run（v92） | **切 1 次**（turn04 @ 24606/27200） |
| e5_diagnose 2 轮 | 0 / 10 段 |
| e5_diagnose 2 轮（背靠背） | 0 / 10 段 |
| e5_full_run（加了武装） | 0 次 |
| e5_full_run | 0 次 |

**两次失败之后连过四次,30 段无切断,当前不可复现。**

## 已排除的解释

**不是外部 stop 命令。** 被切那两段的回执都是 `wav_playback INVALID_STATE`
(即 `stop_requested_` 被置位),而命令列表里那个时间窗内**没有任何 stop 命令**。
能置位它的只剩设备端打断。

**不是"段与段之间没留间隔"。** 诊断脚本原本每段前 stop + 等 4s,零切断;
改成和 E5 一样背靠背连播,**仍然零切断**。间隔不是变量。

**不是房间噪声——至少没有证据。** 第一次失败后立刻测底噪,
`idle_clean` 最大 7.0、均值 3.7,远低于门限 40。
**但这是事后测的,说明不了切断那一刻。**

## 我不知道成因，也不打算编一个

最后剩下的系统性差别是诊断脚本每段都调 `click_arm`。给 E5 也加上之后就不切了——
但**这个相关性没有机制支撑**:`afe_click_arm()` 只是置 `s_click_armed` 并复位计数器,
`click_scan()` 不碰打断门限用到的任何状态。
**没有机制的相关性,在 6 次运行的样本上,和巧合区分不开。**

更可能的解释是那两次运行期间房间里有过短暂声响,而之后一直安静。
**但"更可能"不是"已确认"**,我今天已经因为把一个没实测的解释写进日志而付出过代价。

## 做了什么

**把下一次失败变成可诊断的。** `e5_full_run` 现在每段开播后武装门限计数器,
一旦发生切断,立刻读回 `frames / loud / speech / both / max_rms`:

- `max_rms` 远高于门限 40 → AFE 输出里真的有类语音内容(残余回声漏过,或房间有声)
- `max_rms` 刚过门限 → 只是擦边

**在拿到那组数之前,E5 的状态是"当前通过,但有两次未解释的失败",不是"通过"。**

## 一个流程上的教训

前四次 E5(v78/v85/v88 各一次,加今天若干)都是 0 次切断,我已经开始把它当成
"这一项稳了"。**连续通过会让人把判据当背景音**,直到它失败才想起来它本来在测什么。
这次值得记住的不是那两次失败,而是**我需要它失败才想起去装归因计数器**——
而那本该在第一次运行时就装上。
