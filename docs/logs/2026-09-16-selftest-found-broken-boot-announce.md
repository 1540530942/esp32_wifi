# 2026-09-16 · 开机自检第一天就抓到一个长期存在的真 bug

## 自检报的是对的

自检上线后一直报 `TOO QUIET peak=-84.3`(后来 -90.3)。-84.3 dBFS 是**绝对静音**。
追下去发现它**没有误报**——回采确实什么都没收到,因为**开机播报从来就没播出来过**:

```
play_audio failed  stage=wav_playback  error=ESP_ERR_NOT_SUPPORTED
```

设备的 raw-HTTP WAV 路径硬性要求 **PCM / 单声道 / 16bit / 16000Hz**:

```c
if (!fmt_seen || format != 1 || channels != 1 || bits_per_sample != 16 ||
    sample_rate != AUDIO_OUTPUT_SAMPLE_RATE || audio_remaining == 0)
    return ESP_ERR_NOT_SUPPORTED;
```

而云端 TTS 出的是 **24000 Hz**(下载实测:24000 Hz / 单声道 / 16bit / 7.60s)。
**每次开机播报都被拒,一个采样都没播。**

### 它坏在最难被发现的方式上

**没声音和"它今天没话说"看起来一模一样。** 没有任何报错会传到人眼前。
坏了多久不知道,但 E5 的脚本注释里至今还写着
「设备重启后会播报"今天是9月14日,星期一,固件版本…"」——**描述的是一个早已不工作的功能**。

### 修法

修在云端:存盘前重采样到 16kHz。这遵循任务清单自己定下的约定——
「ESP32 侧只有 5 个 assistant 文件的 **16kHz 转码版本**(codec 硬性要求)」,
**设备就该被喂 16kHz**。

验证:播报命令状态变成 `done`,回采收到信号。

## 自检本身前后错了三次

| 版本 | 读数 | 错在哪 |
|---|---|---|
| v89 | -84.3 | **在声音还不存在时测**：`boot_announce()` 只是发 POST，云端合成后才回发播放命令 |
| v90/v91 | -90.3 | **值已被心跳读走**：`afe_ref_level()` 破坏性读取，而心跳每 5s 也在读，**一个破坏性读取不能有两个消费者** |
| v92 | **ok peak=-35.4 @vol40** | 判据用错音量：播报按 40% 播，拿工作音量的带宽判会**永远报警** |

第三次那个尤其要记:播报电平 -35.4 dBFS 对 40% 音量**完全正常**
(扫描表 vol60 → -19.0、vol70 → -14.0)。**一个永远在报警的检查等于没有检查。**
现在只判开机时真正值得抓的两件事——**回采削顶** 或 **回环死掉**——
并把峰值连同音量一起报出来,让校准在它该被判的音量上判。

### 关键在于它失败得很响

三次都是因为它报了一个**不可能的数**(-84.3 / -90.3 = 绝对静音)才被追下去。
**一个实现得半对的检查,仍然抓到了一个真 bug;
如果它当初"合理地通过"了,开机播报到现在还是坏的。**

## 一个我解释不了的开放问题

**每次开机产生两条播报**,相隔约 12 秒,文件名不同(即两次独立生成):

```
12:33:21  done    boot-b4b967c1217523c7.wav
12:33:33  failed  boot-0a6152d9fb9151ea.wav   ← stage=wav_start INVALID_STATE（播放器还忙）
11:13:03  done    boot-a51ad33ec4e7ac8d.wav
11:13:12  failed  boot-815b88c65c46fe61.wav
```

设备侧只调用一次 `boot_announce()`(app_main 仅 1 处);服务端有两个路由但没有别的调用方。
`post_json` 有一条"HTTPS 失败则回落明文 HTTP 重发"的路径,**形状正好能产生两次**——
但 hub 的访问日志里**查不到这两个 POST**(容器 11:12 启动,时间窗覆盖得到),
所以这个猜测没有证据支持。

**我不给它一个编出来的结论。** 今天已经因为"任务队列 8 秒"吃过一次亏:
一个没有实测支撑的解释,写进日志之后就会被后来的自己当成事实。

影响:每次开机留一条 `failed`。功能上无害,但**它是会掩盖真故障的噪声**——
今天的 bug 正是藏在一堆 `failed` 里才没人看。记为待查。
