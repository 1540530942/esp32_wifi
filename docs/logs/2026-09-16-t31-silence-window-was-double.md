# 2026-09-16 · T3.1 的静音窗口一直是 640ms，判据要的是 320ms

## 这是今天第一处真实的判据不符

前面推翻的五条结论**全是我自己测量的问题**。这一条不同:
**固件的实际行为和任务清单的规格不一致,而且我一直把它记为通过。**

## 怎么发现的

T3.1 判据:「连续约 **320ms** 静音触发结束」。设备报 `silence_frames=20`。
**20 帧等于多少毫秒,取决于帧长**——而我从来没验证过帧长,一直按 16ms 算,
得出 320ms,然后打勾。

想验证时先试了从采集数据反推:`clean` 通道总比 `mic` 少一截,
差值集合是 {0, 256, 512}。我第一反应是"块长整除 256"。**这个推理是反的**:
少掉的是**没取完**的那一块,所以缺口必然**小于**块长——观察到缺口 512,
说明块长 **大于** 512。

于是让设备直接报:

```
feed_chunk=256  fetch_chunk=512  frame_ms=32.0  silence_ms=640
```

**打断计的是 fetch 块(512 样本 = 32ms),不是 feed 块(256)。**
`silence_frames=20` 实际是 **640ms,判据的两倍**。

Kconfig 的帮助文字和源码注释里都白纸黑字写着「at the AFE's ~16 ms frame」——
**错误假设被写进注释,就变成了后来者(包括我自己)不再质疑的"依据"。**

## 修改与回归

`AEC_BARGEIN_SILENCE_FRAMES` 默认 20 → **10**,实测 `silence_ms=320`。

当初选 20 是为了避免"在用户音节间隙里来回抖动",所以改小必须验回归:

| 回归项 | v88 结果 |
|---|---|
| E5 误打断 | **0 次 / 127.52s**，5/5 轮完整 |
| E4 打断触发 | **8/8** |
| E4 延迟 | 中位 148ms（120–151） |

没有抖动迹象,也没有误打断。原因也说得通:`playback_barge_in()` 是**停播**不是压低音量,
停播后 `playing` 变假,`ducked` 立刻复位,那条"静音多久才解除"的路径**很少真正走到**——
它只在"压低了但还在播"的误触发恢复场景下生效。

## 教训

和一小时前的「8 秒队列」是同一个:**一个没有实测支撑的数字,被写进注释和日志之后,
就获得了它本来没有的权威。** 区别在于这次它掩盖的不是我的测量错误,
而是**系统真的没有按规格做事**,而且掩盖了很久。

顺带:我那次"从缺口反推块长"的推理方向是错的,幸好没有据此下结论。
**推理能给出假设,不能给出数据。**
