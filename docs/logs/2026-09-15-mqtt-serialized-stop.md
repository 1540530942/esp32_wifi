# 2026-09-15 · 把命令搬上 MQTT 之后，云侧停播反而失效了

## 我自己造成的回归

上一条改动把通用命令端点接上 MQTT，下发从 10.9s 降到 169ms。
**代价是命令被串行排到了播放后面**，而我是在复测 E4 时才发现的。

实测（turn10，37.9s，起播 3s 后发 stop_audio）：

```
stop_audio 被处理: +36.1s
播放结束:         +36.1s
```

**停播命令在这段音频自己放完之后才被处理，它什么也没停到。**

`click_arm` 同理：起播 2s 后发出，+27.2s 才被处理，而播放 +25.3s 就结束了。
E4 的七次运行全部作废在 `click_arm never acknowledged`，根因就是这个。

## 为什么以前没事

MQTT 侧只有一个 `mqtt_cmd` worker 任务，而 `play_audio` 的处理函数会把它占满整段：

```cpp
while (player->is_playing()) { vTaskDelay(pdMS_TO_TICKS(20)); }   // app_main.cpp:690
```

**这个串行化一直存在，只是以前够不着**：命令原先走心跳响应，由主循环任务处理，
那是另一个任务，从来不会被播放阻塞。我把命令挪到 MQTT 上，等于把它们
挪进了那个会被播放堵死的任务里。

**性能改进把一个潜伏的结构问题变成了功能故障。** 这类回归不会在"改得对不对"
的层面暴露——publish 是对的，延迟确实降了 64 倍——它只在**别的东西恰好共用
同一个任务**时才显形。

## 修法

在 MQTT 事件回调里对**已确认非阻塞**的命令直接就地执行，不进队列：

- `stop_audio` / `stop` —— `AudioPlayer::stop()` 只置一个原子标志和时间戳就返回
- `click_arm` / `click_result` —— 只读写 AFE 的几个状态变量

就地执行是安全的，理由和**设备端打断能从 AFE 任务里停播是同一个**：停播本身
不是阻塞工作。

**刻意做成白名单，而不是"除了 play_audio 以外都就地执行"**：`ota` 和
`stream_prepare` 同样有长耗时工作，把未经审查的处理函数放到 MQTT 事件任务上
会把连接本身卡住。

就地路径完整复刻了 worker 的回执顺序（先 `accepted`、再带 action 的终态），
否则 hub 永远等不到终态，会把命令按超时作废。

## 附：那次"误打断"其实是判对了

同期发现播放被随机切断，`idle_clean` 爆发到 79–95，越过门限 40。
我一度写成"能量门限是绝对值、不随底噪自适应"的设计弱点，并准备改自适应门限。

**实际是屋里有人在打电话。**

所以那不是误触发，是 E4 要求的正确行为：有人说话 → 麦克风收到人声 → 打断触发。
按 4× 自适应改门限反而会把这次**正确的打断**压掉（门限升到 316，人声 218 就
打不断了），是把功能改坏。

同期那个 `erle_db=8.0` 也是同一个原因造成的无效读数——人声抬高了 `clean` 项。
房间安静后复测：

| | 有人打电话 | 安静后 |
|---|---|---|
| `idle_clean` | 15 / 20 / 35 / **79–95** | 1.5 / 1.0 / 8.0 / 1.8 / 1.2 |
| `erle_db` | 0 / 8.0 / 20.7 / 29.3 | **38.2 / 44.4 / 42.3 / 48.3 / 51.3** |

门限 40 稳稳落在底噪 2.7 和人声 218 之间，**原判据成立，不需要改**。

教训：**在承认一个"设计缺陷"之前，先确认测量条件。** 我差一点把一次正确行为
当成 bug 修掉。

## 另外清掉的东西

broker 上还压着 **66 条陈旧 retained 命令**（最老的是前一天的 `play_audio`，
还有两条挂了 24 小时的 `ota`）。设备每次重连都会收到整批重放——重启不但没修好
播放，反而因为重启就是一次重连而更糟。

`purge_retained_commands.py` 早就写好了，**但从来没跑过**。又一次"写完了不等于
生效了"。顺手把它改成**同时向 broker 查询**当前保留的主题，而不只读
`devices.json` 的记录：两者会分叉，hub 重新部署或数据文件恢复都会丢掉 id，
而那些 retained 消息还在 broker 上继续重放。已清 66/66，通配符订阅现在返回空。
