# 2026-09-19 · 找到了真正的复位原因：欠压（BROWNOUT），不是"芯片死了"

## 决定性新证据

例行检查心跳时发现设备刚重启（uptime 仅几分钟），且过去 6 小时没有任何
OTA 或人工命令触发这次重启。查 `reset_reason`（早就在心跳里，只是之前没
系统性去读）：

```
reset_reason = 9 = ESP_RST_BROWNOUT
```

**这是 ESP32 芯片自带欠压检测器触发的硬件复位，不是我的操作，不是用户
断电，是真实的电压跌落事件。**

## 这改写了昨天的诊断方向

昨天的结论是"总线电气健康、两颗芯片零应答，只剩供电或芯片本身两种可能"，
建议的下一步是"找 codec 的 VDD 引脚接线测量"。**这次的证据说该查的可能
不是某颗芯片专属的电源轨，而是整机供电本身**：

- 两颗芯片同时失效 + 断电重启也没用 + 现在抓到真实的 BROWNOUT 复位，
  三件事拼起来，指向一个不稳定/不够用的电源（适配器、USB 线、接头），
  而不是某颗芯片物理损坏。
- 欠压复位不是"复位一次就完事"——电压如果持续不够，芯片会反复卡在
  复位态，可能连串口输出都来不及打印。这和之前那次"5 小时零输出、
  断电重启无效"的现象完全吻合：**很可能那 5 小时也是同一种欠压反复
  复位，只是当时没人查 reset_reason，被我误判成"静默死锁"。**

## 但不要过早乐观：追加验证发现是噪声，不是芯片恢复

复位后第一次扫描：`ACK from: 0x41 0x45`。0x41 精确等于 ES7210 配置地址
0x82 右移一位，我一度以为"ES7210 复电后真的在响应了"。

**连续追加 5 次扫描，间隔约 8 秒**：

```
0x3B   0x41   0x1D   0x18   0x41
```

**每次只有一个地址应答，而且换来换去**，其中 0x3B、0x1D 不对应任何已知
器件。这个模式是电气噪声的特征，不是真实器件应答——供电不稳到让 I²C
信号线产生随机的类应答脉冲。**我上面"0x41 就是 ES7210"那个判断收回**：
5 个样本里巧合命中已知地址 2 次，和纯噪声的概率完全对得上，不能当证据。

`es7210_regs` 寄存器读取仍然失败（`i2c read err r43=270 r44=270`），
心跳里这次开机的 `codec_failed=true, fail_count=3` 也没变——**芯片本质上
仍未恢复正常工作，只是总线在噪声中偶尔产生看似应答的电平。**

## 结论与下一步

- **确凿**：这次是真实的硬件欠压复位（reset_reason=9），不是我或用户的
  操作，很可能也是此前"5 小时静默"的真正成因。
- **推测但有依据**：供电本身不稳定/不够用，而不是某颗芯片物理损坏——
  两颗芯片同时受影响、扫描噪声在总线上出现，都更符合"电源问题"而非
  "单个元件损坏"。
- **收回**：芯片"复电后开始响应"的说法不成立，那是噪声，不是恢复。

## 给用户的下一步，和昨天不同

昨天建议"找 codec 的 VDD 引脚接线测量"。**现在优先级改为先查整机供电**：

1. 换一根质量更好、电流余量更大的 USB 数据线（细线/劣质线在负载下压降
   明显，是这个现象最常见的成因）
2. 换一个电源适配器/USB 口（如果是从电脑 USB 口供电，尝试真正的 5V/2A
   以上适配器）
3. 检查电源接口有没有松动、氧化、虚焊

`adc_read`（GPIO9）仍然保留，如果换电源后问题依旧，再回到"测某颗芯片
专属供电轨"这条路径。
