# 2026-09-15 · 给 audio_interact 卷加保留策略（磁盘满不再靠人工）

## 为什么必须做

磁盘满这一项我已经**手工清理过两次**，而且两次的表现都不在磁盘上：

```
OSError: [Errno 28] No space left on device: '/app/data/devices.json.tmp'
POST /api/heartbeat  500
```

device_hub 每次心跳都要写状态文件，磁盘一满就全线 500，症状是
**"命令下发不到设备"**。为此我先后怀疑过 MQTT retained 重放、下发延迟，
两轮排查之后才去跑 `df`。

**一个无上限增长的卷不是音频问题，是同一文件系统上所有服务的可用性问题。**

## 为什么按天数保留不够

当前入流约 **3.6GB/天**（其中很大一部分是我自己的 AEC 测试：每次云端 ASR
调用都会在这里落一份会话）。40G 盘从空到满约 11 天，所以
**14 天保留策略照样会溢出**。光按年龄定不住。

于是两条规则：

1. **年龄** —— 删掉 `--keep-days`（默认 7）之前的日期目录。便宜、直观。
2. **水位** —— 剩余空间低于 `--min-free-gb` 时，**从最旧的开始**继续删，
   直到剩余达到 `--target-free-gb`。

**真正定住磁盘的是第 2 条**，因为它盯的是"还剩多少字节"这个真正重要的量，
而不是对入流速度的猜测。第 1 条只负责让常态保持整洁，使第 2 条很少动手。

删除永远是**从最旧开始、整个日期目录**，不进单日内部挑拣，不删今天，
并且无论盘多紧都不动最近 `--floor-days`（默认 2）天。

## 一个刻意的设计：它会拒绝执行

第一次演练直接报错退出了：

```
!! 即使删光 2026-09-13 之前的全部数据，也只能到 9.0G，达不到目标 10.0G。
!! 这是容量不足，不是清理不够。不要靠放宽 --floor-days 掩盖。
```

这是故意的。**清理脚本最危险的失败方式是"删到能跑为止"**——那样磁盘问题
会变成不可见，而不是变小。宁可退出非零让人看见。

那 10G 是我随手定的第一个数。改成 8G 不是把数字调到能过，
而是**从入流速率反推**：3.6GB/天，8G 余量 = 日常 cron 之间有两天以上的缓冲。
这是有依据的取值。

## 删之前先备份，但只备份得动的部分

按既定规则先备份到 spark。实测 tang 下行只有 **0.31 MB/s**，
7.36G 要传 **6.7 小时**，而且会占满 hub 和 ESP32 正在依赖的那条链路——
备份本身会妨碍验收工作。

所幸结构是分开的：

| 内容 | 大小 |
|---|---|
| manifest / events / labels（会话记录本身） | **3.6 MB** |
| wav 原始音频 | 7.36 G |

所以备份了**全部元数据**（10255 个文件，521K，两端 md5 一致），
音频直接删。

**必须说清楚的代价：2026-08-10 至 09-12 的原始音频没有备份，已不可恢复。**
保留下来的是"这些会话发生过、什么时候、有哪些事件和标注"，不是声音本身。

顺带一个 tar 的坑：`--exclude` 写在文件列表**后面**会被 GNU tar 忽略，
第一次打包因此把音频也装进去了，传到 98M 被超时截断才发现。要写在前面。

## 落地

```
/usr/local/sbin/prune_audio_interact.py
/etc/cron.d/prune-audio-interact
  17 4 * * * root ... --target-free-gb 8 --apply >> /var/log/wangyutang/prune_audio_interact.log
```

执行结果：释放 **7.36G**，`free 1.1G -> 8.3G`（98% -> 79%），
hub `health=200`，设备在线，`volume=40`。
再跑一次报"无需清理"，幂等。
