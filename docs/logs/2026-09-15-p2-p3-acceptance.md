# 2026-09-15 · P2/P3 验收：B0、E2b、E3、E5 通过，E4 定位到根因

树莓派恢复后一次性推进了全部剩余实验。本篇记实测数据和推导过程；基础设施侧的
故障（TLS、HTTPS 响应体、WS 锁风暴、磁盘满）见同日另两篇。

**最终目标不变：机器人说话时用户开口，200ms 内停播。**

## B0 声学耦合（不在原清单，是我加的前置关）

上一轮 E2b 失败的真因不是 AEC，是树莓派的声音根本没到麦克风（`pre_rms` 24.0 对
底噪 17.5，只高 2.7 dB，两路 ASR 全空）。所以先量耦合再做实验。

| | pre_rms |
|---|---|
| 底噪（全静音） | **15.8** |
| 树莓派放音 @vol100 | **396.1** |

余量 = 20·log₁₀(396.1/15.8) = **28.0 dB**（自定目标 ≥15 dB）。**通过。**

树莓派此时已回到 `192.168.1.17` / SSID `1-1-1204`，与 ESP32 同网段（之前在
`172.20.10.5` 手机热点）。

## E2b 反向对照 —— 通过

ESP32 静音，树莓派播 turn03。`erle_full_db = 0.25`，post_rms 384.7 对 pre_rms
396.1 —— **没有回声要消时，AFE 几乎不衰减目标人声**。

ASR 对比（任务书判据"识别率不下降"，用云侧 ASR 判）：

```
mic_raw  : 说了，晋太原中，武陵人捕鱼为业。缘溪行，忘路之远近。忽逢桃花林，
           夹岸数百步，中无杂树，芳草鲜美，落英缤纷。渔人甚异之。
clean_aec: 说了，晋太原中，武陵人捕鱼为业。缘溪行，忘路之远近。忽逢桃花林，
           夹岸数百步，中无杂树，芳草鲜美，落英缤纷，渔人甚异。
```

逐字一致，仅末尾少一个"之"——clean 比 mic 少 256 个样本，是采集窗口截断，不是
AFE 压制。三条判据（语音段一致、无压制无断续、ASR 不下降）全过。

## E3 双讲（核心）—— 通过，且超出判据

ESP32 播 turn04 @vol80，第 10s 树莓派插播 turn05。

```
mic_raw  : 陶渊明的《桃花源记》，这段文字描写了武陵渔人沿溪而行。
           对的，这是我喜欢的陶渊明诗人，你来背诵另外一首。
clean_aec: 对的，这是我喜欢的陶渊明诗人，你来背诵另外一首。
```

判据是"人声清晰可辨"。实测**人声逐字保留，而机器人自己的话在 AFE 输出里完全
消失**——ASR 已经读不到它。

## E5 误打断 —— 通过（但中途出现过回归，见下）

v59/v60 各验一次，树莓派全程静音，ESP32 播 turn04：**提前路径 0 次、AFE 路径 0 次**。

### 中途的回归：机器人打断了自己

v58 上抓串口发现：

```
audio_player: starting WAV playback at 80%
afe: local barge-in -> duck+stop
audio_player: playback position: written=576ms played=548ms dropped=10ms
```

**机器人在自己开口 576ms 处把自己打断了。** 这直接让 E4 无法测量——等人真开口时
已经没有东西可打断，表现为"检出咔哒、无打断"。

根因：onset grace 是 500ms，而 E1 实测 AEC 收敛需 **0.4–0.5s**，grace 正好卡在
收敛边界，残余回声被 VAD 判成人声。按任务书指示（「调 VAD 门控，不要直接调 AEC」）
把 grace 提到 **900ms**（约两倍收敛时间）。这不增加打断延迟，只推迟"开口后多久
可以被打断"。

## E4 打断延迟 —— 未通过，根因已定位

### 实测

| 固件 | 有效样本 | 结论 |
|---|---|---|
| v59（仅 AFE VAD 路径） | 305, 319 ms | 不及格 |
| v60（加提前路径，判据写错） | 30, 194, 289 ms | 中位数 194ms 踩线，离散过大 |

### 预算拆解

| 环节 | 耗时 | 依据 |
|---|---|---|
| 咔哒 → 语音起点 | ~10ms | 素材保护带 |
| **AFE 内部 + VAD 判定** | **~210ms** | 差值推算 |
| 4 帧持续语音门限 | 64ms | 配置 |
| 停播 | 24ms | T3.2 实测 |

任务书给 "AFE + VAD" 的预算是 **50ms，实际约 210ms** —— 这一项就是全部超标量。
`SPEECH_FRAMES` 4→3 只省 16ms，救不回来。

### 修法：把触发点移到 AFE 之前

E4 的咔哒检测器已经在 `feed_task` 里、AFE 之前回答了打断真正要问的问题：
**ch0 涨了而 ch1 没涨 ⇒ 发声的不是机器人**。加"连续 3 帧"（≈48ms，正是 T3.1 给的
语音起始门限）就从瞬变检测器变成语音起始检测器，整条 210ms 的 AFE 流水线不在路径上。

原有 AFE VAD 路径原样保留，新路径只可能更早触发。

### v60 的判据写错了（同一类错误的第三次）

```c
peak > (peak_ref + 1) * 4.0     // 错
```

机器人大声时 `peak_ref` 可达数千，这个式子要求 ch0 超过满量程，**永不成立**——
只有音节间隙才偶然触发，这就是 30ms 与 289ms 并存的原因。

正确写法（`click_scan` 里本来就是对的，我没照抄）：比**比值相对于它自己的包络**。
回声路径增益大致固定，那个running 比值就是增益，外部说话人正是把比值顶上去的东西。

**这是同一类错误的第三次**：v48 用 ch0 比自己的包络、v49 用 ch1 比自己的包络、
v60 用 ch0 比 ch1 的固定倍数。每次都是**拿一个绝对阈值代替两个通道之间的关系**。

v61 已修，待验。

## 测量方法上的两个必需品

1. **`check_robot_still.py`** —— 树莓派就是机器人，`codex-loop-camera-check` 会周期性
   驱动它前后左右移动，一动声学耦合就变。每次采集后回查任务队列，窗口内有 `move_*`
   就作废重测。不去关别人的循环。

2. **`e4_latency.py` 的逐步确认** —— 命令下发不可靠（`mqtt_control: pubdbg ...
   status=failed`），"机器人根本没在播"和"打断失败"的日志几乎一样，都是
   "检出咔哒、无打断"。脚本确认每一步，确认不了就作废而不是报失败。
   实测 5 次里 3 次、6 次里 5 次被作废——**如果不作废，这些会被误报成 E4 不及格**。

   还有一个隐蔽的作废原因：等 `click_arm` 回执可能耗时几十秒，把树莓派说话推到了
   素材播完之后。已改为触发前重新确认 `audio_playing`，并改用最长的 turn10。
