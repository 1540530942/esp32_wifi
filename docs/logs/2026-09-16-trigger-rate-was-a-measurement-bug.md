# 2026-09-16 · 那个 50% 触发率不存在：是判据把成功记成了失败

| 测法 | 结果 |
|---|---|
| 树莓派走任务队列 + 咔哒判据 | 50% → 60% |
| 树莓派走 ssh aplay + 咔哒判据 | **42%** |
| 树莓派走 ssh aplay + **播放命令判据** | **100%（12/12）** |
| 同上，**无人插话对照组** | **0%（6/6）** |

**打断每次都触发。之前报的漏触发全是我自己的判据造出来的。**

## 两层错误叠在一起

### 第一层：仪器太慢

插话走 `/action/api/tasks` 下发,**从下发到出声约 8 秒**,而脚本只等 12 秒就去读结果。
插话经常落在观察窗的边缘甚至窗外。**那个数与其说反映检测器，不如说反映任务队列延迟。**

改 ssh 直发 `aplay`,下达到出声 <1s,且阻塞到播完——窗口才成为已知量。

### 第二层（真正的元凶）：判据只认咔哒

`click_result` 只在 `s_click_us != 0 && s_click_duck_us == 0` 时记录延迟,
即**咔哒必须先于打断被识别出来**。

但打断在**第一帧合格语音**就触发,而咔哒检测器要先满足包络比值条件。
**打断跑赢咔哒是常态**,这时 `s_click_duck_us` 保持 0,回执写"no barge-in yet"——
**机器人明明停了,却被记成漏触发。**

归因计数器其实早就把矛盾摆在脸上了:多次"漏触发"报 `both=1`,
即门限两个条件同时满足过一帧,而 `speech_frames=1` 只要一帧就该触发。
**我当时没有追这个矛盾,而是去找"为什么 VAD 不认"**,差点据此去放松 AFE 的 NS 参数——
那会为了一个不存在的问题,把一个工作正常的系统调坏。

## 中间还澄清了一件事

`both=1` 不触发有两种解释:构建用的帧数门限不是 1,或者 `ducked` latch 还没复位。
**看源码分不出来**:本地 `sdkconfig`(gitignored)写的是 4,而 CI 构建用的 Kconfig 默认是 1,
设备跑的是 CI 的产物。

所以把打断常量加进了心跳可读的配置回执,不再猜。设备实测:

```
vad_mode=3 vad_min_speech=48 vad_delay=128
grace=1500 min_rms=40 speech_frames=1 silence_frames=20
```

`speech_frames=1` 坐实——于是"配置不同"被排除,剩下的只能是判据错,这才找对方向。

## 新判据，以及为什么敢信 100%

判据换成**播放命令是否提前以 `failed|stage=wav_playback` 结束**:

- 自然播完报 `done` → 判为本轮无效(说明流程超时了,不能算成功打断)
- 被停报 `failed` → 判为触发
- `audio_playing` 不用,它随心跳走,最多 5s 陈旧

**100% 这种数必须先证伪再相信**,所以加了无人插话的对照组:同样的流程、同样的窗口,
只是不放声音。结果 **0%(6/6)**——判据不会对任何情况都喊"触发"。

## 教训

这是今天第三次「演示是好的、测量是坏的」:
昨晚按文件名找回放命令找不到、今早按绝对电平找回放段找不到、现在按咔哒找打断找不到。

共同点是**我的判据都比被测对象更脆弱**,而每次失败都长得像被测对象坏了。
`both=1` 那个矛盾是明摆着的线索,我却绕过它去解释一个不存在的现象。
**下次再遇到"计数器说满足了、结果却没发生",先怀疑判据,别急着解释现象。**

## 对之前结论的修正

- E4 的「中位 144ms」**不再是有偏的**:它作废的那些样本不是难样本,是判据错认的成功样本
- 「漏触发是最终目标的短板」这个结论**撤销**
- 放松 AFE NS/残余抑制的计划**取消**,没有依据
