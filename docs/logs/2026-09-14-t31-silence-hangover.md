# 2026-09-14 · T3.1 复查：结束条件差了 20 倍

## 起因

树莓派仍然掉线，E2b/E3/E4 全部卡住。按"不要空转"的要求回头逐条复查 P3，发现 T3.1
一直被当成"已实现"，但它其实写了**两个**门限：

> T3.1 本地 VAD 判定：连续约 48ms 有人声触发开始，连续约 320ms 静音触发结束。

**开始那半实现了，结束那半没有。**

## 实际代码

`afe_pipeline.c` 的 `fetch_task`：

```c
if (playing && past_grace && res->vad_state == VAD_SPEECH) {
    if (++speech_run >= CONFIG_AEC_BARGEIN_SPEECH_FRAMES && !ducked) { ... }
} else {
    speech_run = 0;
    if (ducked && !playing) { ducked = false; }
    else if (ducked && res->vad_state != VAD_SPEECH) {
        playback_unduck();        // ← 第一个非语音帧就恢复
        ducked = false;
    }
}
```

开始：4 帧 × ~16ms ≈ 64ms（任务书说 ~48ms，量级对）。
结束：**1 帧 ≈ 16ms**（任务书说 ~320ms）。**差了 20 倍。**

## 为什么这是真问题，不是纸面差异

自然语音的音节间隙轻易超过 16ms。所以用户正在说话打断机器人的过程中，AFE 的 VAD
会反复掉出语音态，于是：

```
用户: "等——      一下——      我想问"
机器人音量: 压低 → 弹回 → 压低 → 弹回 → 压低
```

**机器人会一边被打断一边把音量弹回去。** 这正好是"用户还在说话"时最不该做的事。

而且这个行为**不会被任何现有验收指标抓到**：

- E5 测的是"误打断次数"，这里压根没有多余的打断，计数仍是 0
- 打断延迟（E4）测的是第一次压低的时刻，弹回发生在之后，测不到
- 播放时长、`spk_played_ms` 也都正常

只有真正去听、或者去读这段状态机才会发现。

## 修法

新增 `CONFIG_AEC_BARGEIN_SILENCE_FRAMES`，默认 20（≈320ms），要求**连续**静音才恢复：

```c
if (++silence_run >= CONFIG_AEC_BARGEIN_SILENCE_FRAMES) {
    ESP_LOGI(TAG, "barge-in ended: %d silent frames -> unduck", silence_run);
    playback_unduck();
    ducked = false;
    silence_run = 0;
}
```

并且任何一帧语音都把 `silence_run` 清零——"连续"必须是真的连续。

**两个门限的不对称是有意的**：开始要快（4 帧），结束要迟疑（20 帧）。判错方向的代价
不一样：晚 300ms 恢复音量用户几乎无感，早 300ms 恢复则是在用户说话中途插嘴回去。
