# 2026-09-16 · 补验 P0 的 T0.2 / T0.3，并更正一个我反复写错的归因

## 为什么这两项一直没验

T0.2 和 T0.3 都是**树莓派任务侧**的修复,而我今天全程用 ssh `aplay` 绕开了那条路径。
**绕过去测,等于没测那条路。** 之前几轮的验收表里它们被当作"早就通过"带过了。

## T0.2 —— 长素材不被 8 秒 timeout 砍断

走任务队列播 `turn03_user.wav`(93.12s):

```
+   0.4s status=claimed
+  97.2s status=complete
claim_latency=0.007  completion_latency=93.784  error=无
```

`completion_latency=93.784s` 对上素材的 93.12s。**通过。**

## T0.3 —— 播放失败要上报，不能挂住

故意请求一个不存在的素材:

```
+ 1.4s status=failed
error = play_local_audio: not found: __does_not_exist__.wav
```

**通过。** 1.4s 内拿到终态,错误信息明确,没有挂在队列里。

## 更正：「任务队列有 8 秒延迟」是错的

T0.2 的回执里 `claim_latency=0.007` 让我起疑,于是实测了一遍:
树莓派录音,我发任务,量从 POST 到实际出声的间隔。

```
任务下发于录音第 4.3s
实际出声于录音第 5.7s
=> 1.4s
```

**1.4 秒,不是 8 秒。**

我把"约 8 秒"写进了三条提交信息、四篇日志和四个脚本的注释,
当作"测量被污染"的主因。那个数来自对 `verify_replay_level` 第一次运行时间线的
**一次误读**,我没有实测就把它当成了事实,然后在后续每一篇里复用。

### 当时就有反证，我没当回事

换成 ssh 直发之后,触发率从 50–60% **掉到 42%**。
**如果队列真是主因,换掉它应该变好。** 我当时写下"更差了",却仍然把账记在队列上。

真正且唯一的成因是**判据只认咔哒**:同样的 ssh 传输,咔哒判据 42%,
播放命令判据 100%。传输层从头到尾都不是问题。

### 那第一次回放验证为什么失败

也不是传输。那一轮机器人只说了 3.876s 就停了,而树莓派还没出声——
**是房间里别的声音把它打断的**(当时 `idle_clean` 有爆发)。
插话"来晚了"是结果不是原因:机器人早就被停掉了。

## 教训

这和今天其余几条是同一个模式,但更糟:**前面几次是判据比被测对象脆弱,
这次是我把一个没测过的数当成事实,还反复引用它。**

一个没有实测支撑的数字,写进一篇日志是猜测,写进八个地方之后就变成了"已知事实"——
**复述次数不产生证据。**
